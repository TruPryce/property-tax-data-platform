# Tasks

Every module below lives in `libs/property-tax-application/src/property_tax_application/`. Where a
task says a type is **frozen**, it means a frozen slotted dataclass validating in `__post_init__` and
raising `ValueError`, matching the established style of `AcquiredArtifact` and the canonical record
model. Where it says a port is a **Protocol**, it means `@runtime_checkable class X(Protocol)`,
matching `ArtifactSink` and `BronzeStore`.

No task adds a dependency to `property-tax-application`. No task edits a migration, an adapter, or a
county module.

## 1. The shared run vocabulary

<!-- countyforge-task: 1.1 paths=libs/property-tax-application/src/property_tax_application/runs.py checks=repo.check risk=higher_risk prerequisites=D1,D10 -->
- [ ] 1.1 Add the run reference and the lossless outcome — Add `runs.py` carrying `ProcessingRunRef`, a frozen type wrapping one persistence-generated value, whose docstring states in its first line that it is an **opaque locator**: comparable for equality, carrying no ordering, freshness, or precedence meaning, and never canonical identity. Give it equality and hashing and deliberately no ordering methods. Add `ReleaseDiagnosticRecord` (code, optional field name, optional physical row number, optional layout fingerprint) and `ReleaseNoticeRecord` (code, optional field name, optional physical row number), each bounded and carrying no source value; validate `code` against the exact closed vocabulary the accepted contract admits, supplied as a module-level frozen set rather than a second enum, so the vocabulary keeps one authority in the bounded-processing boundary while a value that is valid here is a value that can be recorded — `ingestion.release_diagnostic` carries `CHECK (code IN (...))`, so an unvalidated code would pass the port and fail at the write. Add `ReleaseProcessingOutcome` carrying `disposition` (a `ReleaseDisposition` StrEnum of exactly `accepted` and `rejected`), `boundary_contract_version`, `parser_contract_version`, `layout_fingerprint`, the four counts, the two totals, the two truncation flags, and the two bounded record tuples — every fact `ingestion.release_outcome` requires, so an implementation can write that row from this value alone. Enforce the accepted record's invariants here: parser version and layout fingerprint set together or neither; accepted exactly when the diagnostic count is zero; accepted commits what it staged; accepted rejected no row; rejected commits nothing; committed never exceeds staged; no count negative. State in the module docstring that this is the application's own outcome value because the dependency direction forbids importing the adapters', and that the mapping between them must stay total.

<!-- countyforge-task: 1.2 paths=libs/property-tax-application/src/property_tax_application/runs.py checks=repo.check risk=higher_risk prerequisites=D1,1.1 -->
- [ ] 1.2 Add the run lifecycle port — In `runs.py`, add `ProcessingRunRepository`, a Protocol that starts a run from a `ReleaseIdentity` and the `ManifestRef` of the acquisition the run will read, returning a `ProcessingRunRef`, and that records a run as finished. Every port requiring a run accepts the reference type and never a raw persistence value, so a caller is never required to invent one; an implementation refuses a reference that resolves to no started run rather than creating one implicitly. Do not claim the value cannot be constructed — it is a public frozen type and a Python caller can instantiate it; the guarantee is that nothing asks a caller to, and that an unresolvable reference is refused. Document that the run binds the promoted four-component `ReleaseIdentity` to the indexed acquisition, which is where the two halves of a canonical release meet.

## 1b. Manifest reference

<!-- countyforge-task: 1.3 paths=libs/property-tax-application/src/property_tax_application/bronze.py checks=repo.check risk=higher_risk prerequisites=D1,1.1 -->
- [ ] 1.3 Add the manifest index port — In `bronze.py`, add `ManifestRef`, a frozen opaque locator documented on the same terms as `ProcessingRunRef`, and `ManifestIndex`, a Protocol with one operation that records an acquisition manifest in the queryable index a run binds to and returns its `ManifestRef`, idempotently per acquisition so that one artifact carrying several logical releases yields one reference rather than duplicates. This is deliberately a second manifest port, and the reason belongs in its docstring: `BronzeStore` writes immutable evidence to the object store and returns a **storage locator** — the S3 adapter returns `s3://<bucket>/<sha>.manifest.json` — while a run needs the identity of the relational record, which is generated there, is not derivable from that URI, and is not resolvable from the checksum either because the table carries no unique constraint on it. `BronzeStore` cannot simply gain a method without stopping its existing implementer from satisfying it. Do not change `BronzeStore`.

## 2. Source registry and discovery

- [ ] 2.2 Add discovery, its evidence, and the promotion seam — Add `discovery.py` carrying `PageEvidence`, a bounded frozen carrier for what the source page published about a release, with no unbounded field and no raw page body; `ReleaseCandidate`, holding the source locator, the remote metadata the acquisition contract already models, the source as-of evidence, the page evidence, and the established release facts as the three Bronze-grain components plus an **optional** release identifier; `UnchangedRelease`, the result returned where remote metadata and content identity match an already-acquired release; and `ReleaseDiscovery`, a Protocol returning, per observed release, a candidate or an unchanged result, so a caller can tell "acquire this" from "do nothing" without inspecting values. Add `IncompleteReleaseIdentity`, an exception naming the missing components, and one promotion operation from a `ReleaseCandidate` to a `ReleaseIdentity` that raises it when the identifier was never established. This promotion is the single place an incomplete release becomes a complete one; `ReleaseIdentity` is not weakened to admit a partial value, and no downstream port carries a "maybe complete" identity. Do not perform or model county parsing here.

## 3. Canonical persistence

<!-- countyforge-task: 3.1 paths=libs/property-tax-application/src/property_tax_application/canonical.py checks=repo.check risk=higher_risk prerequisites=D2,D5,D6,1.1 -->
- [ ] 3.1 Add the batch, its correlation, and the completion — Add `canonical.py` carrying `CorrelationHandle`, a frozen session-local value whose docstring states that it is neither domain identity nor persistence identity: it exists only to let a record name a parent written in an earlier batch of the same account, it never appears in a stored row, and it stops being valid once its account is complete. Add `CanonicalRecordBatch`, a bounded batch of canonical records in which a record whose parent is not present in the same batch names it by handle. Do **not** require a batch to carry an account's complete descent: the canonical model places no maximum on how many owners, allocations, values, exemptions, land records, improvements, or geometries an account may carry, so a whole-account batch would be bounded only by the largest account in the release, and inventing a maximum child count no accepted contract establishes would be worse. Do not assume every relation hangs off the snapshot — `canonical.owner_value_allocation` deliberately carries no `snapshot_key` and reaches its snapshot through its association, so an allocation's parent chain is two links deep. Use no generic mapping, JSON payload, free-form metadata attribute, or database-shaped row type, and define no key over observed values. Add `ReleaseLoadCompletion`, carrying the `ProcessingRunRef` and `already_complete: bool`.

<!-- countyforge-task: 3.2 paths=libs/property-tax-application/src/property_tax_application/canonical.py checks=repo.check risk=higher_risk prerequisites=D2,D3,D4,1.2,3.1 -->
- [ ] 3.2 Add the canonical load session and repository — In `canonical.py`, add `ReleaseLoadSession`, a Protocol with `__enter__`, `__exit__` annotated `-> None` so a failure cannot be suppressed, `write(batch)` accepting successive bounded batches with nothing durable until completion, an operation declaring an account complete so the handles it introduced may be released, `abort()` leaving zero canonical records, and `commit()` returning a `ReleaseLoadCompletion`. Document that correlation state is bounded by the accounts currently open rather than by the release, that naming a handle after its account is complete is refused, and that one account may span as many batches as it needs so neither side holds a whole account. Add `CanonicalReleaseRepository`, a Protocol whose one method opens a session for a `ReleaseIdentity`, a `ProcessingRunRef`, and a `ReleaseProcessingOutcome`. It takes a complete identity only and has no incomplete-identity branch, because promotion in task 2.2 is where that failure lives. Document on `commit` that the outcome and the load become durable together at that single point, and why: the database gate requiring an accepted outcome is `DEFERRABLE INITIALLY DEFERRED`, so an implementation splitting them across units of work cannot satisfy it. Document that re-completing an already-completed release and run returns `already_complete=True` and writes nothing further, and that a second distinct run for one release is a new load rather than a retry. Name no schema, table, cursor, connection, transaction, bulk-load mechanism, conflict clause, or surrogate key.
