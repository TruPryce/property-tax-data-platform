# Tasks

Every module below lives in `libs/property-tax-application/src/property_tax_application/`. Where a
task says a type is **frozen**, it means a frozen slotted dataclass validating in `__post_init__` and
raising `ValueError`, matching the established style of `AcquiredArtifact` and the canonical record
model. Where it says a port is a **Protocol**, it means `@runtime_checkable class X(Protocol)`,
matching `ArtifactSink` and `BronzeStore`.

No task adds a dependency to `property-tax-application`. No task edits a migration. One task — 2.1 —
touches the six county source definitions, and only to populate the expected media types the accepted
registry requirement names: a field the type gains is worthless if every county leaves it empty. No county
layout, parser, or acquisition behaviour changes.
Exactly one task — 1.2 — edits an adapter, and only the S3 manifest serialization and storage mechanics
plus their tests: changing what the manifest value carries without changing what is written, or where it
is written, would leave the object-store record missing the very field the change adds, or unable to hold
it at all. No other adapter, and no other file in that adapter, is touched.

**Review scopes** — one scope per review round, per [`reviews/README.md`](reviews/README.md). Each scope is
one contiguous region below, and a marker applies until the next marker or the end of the file:
`run-and-manifest` (group 1; specs `processing-run` and `acquisition-manifest-index`),
`registry-and-discovery` (group 2; spec `source-registry-and-discovery`), `canonical-load` (group 3; spec
`canonical-load-session`), `quality-publication-clock` (groups 4–5; spec
`run-bound-quality-and-publication`), and `surface-and-proof` (groups 6–8; spec `application-port-boundary`,
plus the falsification of every other scope). Implementation of a scope waits for its accepting round or a
recorded authorization, per the ledger.

- [ ] 1.1 Add the run reference and the lossless outcome — Add `runs.py` carrying `ProcessingRunRef`, a frozen type wrapping one persistence-generated value, whose docstring states in its first line that it is an **opaque locator**: comparable for equality, carrying no ordering, freshness, or precedence meaning, and never canonical identity. Add `ReleaseDiagnosticRecord` (code, optional field name, optional physical row number, optional layout fingerprint) and `ReleaseNoticeRecord` (code, optional field name, optional physical row number), each bounded and carrying no source value. Validate the two codes by **different** rules, because the accepted contract and the database treat them differently. A diagnostic code is checked against the exact closed vocabulary, supplied as a module-level frozen set rather than a second enum so the vocabulary keeps one authority in the bounded-processing boundary: `ingestion.release_diagnostic` carries `CHECK (code IN (...))`, so an unvalidated code would pass the port and fail at the write. A notice code is **not** closed — `ingestion.release_notice` carries `CHECK (code ~ '^[a-z][a-z0-9_]{0,63}$')` and `ReleaseNotice` validates against a pattern rather than an enum — so check it against that same bounded lowercase grammar. Do not reuse the diagnostic frozen set for notices; closing an open vocabulary would reject codes the accepted contract admits. Add `ReleaseProcessingOutcome` carrying `disposition` (a `ReleaseDisposition` StrEnum of exactly `accepted` and `rejected`), `boundary_contract_version`, `parser_contract_version`, `layout_fingerprint`, the four counts, the two totals, the two truncation flags, and the two bounded record tuples — every fact `ingestion.release_outcome` requires, so an implementation can write that row from this value alone. Enforce the accepted record's invariants here: parser version and layout fingerprint set together or neither; accepted exactly when the diagnostic count is zero; accepted commits what it staged; accepted rejected no row; rejected commits nothing; committed never exceeds staged; no count negative; and `boundary_contract_version` equal to `BOUNDARY_CONTRACT_VERSION`, a module constant of `1` that mirrors the accepted boundary's constant in `property_tax_adapters.release.outcome` — the application cannot import it, so task 7.1 pins the two equal — because `ingestion.release_outcome` carries `CHECK (boundary_contract_version = 1)` and an unpinned integer would pass the port and abort the canonical completion at persistence. Enforce the **evidence seal** too, which `ingestion.assert_outcome_evidence_agrees` checks at COMMIT: retained diagnostics must equal `least(total_diagnostic_count, 100)` and retained notices `least(total_notice_count, 100)`; `diagnostics_truncated` must equal `total_diagnostic_count > 100` and `notices_truncated` likewise; and every retained diagnostic's layout fingerprint must equal the outcome's, including where the outcome's is absent — the check uses `IS DISTINCT FROM`, so a `NULL` fingerprint under an outcome that has one is a disagreement. The bound is 100 because `diagnostic_index` and `notice_index` are constrained `BETWEEN 0 AND 99`. Without these an outcome declaring one diagnostic and retaining none satisfies every other rule here and then aborts the canonical completion transaction. State in the module docstring that this is the application's own outcome value because the dependency direction forbids importing the adapters', and that the mapping between them must stay total.

- [ ] 1.2 Let an acquisition be manifested before its releases are known — In `bronze.py`, add an explicit `jurisdiction` to `ReleaseManifest` and relax `partitions` to admit an empty tuple, validating that any partition present names the manifest's jurisdiction. Both follow the database rather than inventing anything: `bronze.release_manifest` carries `jurisdiction_code NOT NULL` of its own, and migration `0001` adds `release_manifest_identity UNIQUE (manifest_id, jurisdiction_code)` precisely so `bronze.release_partition` can reference it compositely — the manifest owns the jurisdiction and partitions inherit it, adding only tax year and release kind. The relaxation is why: a source whose release facts live in content is acquired before any partition exists, and inspection can fail before one is ever established, leaving immutable bytes with no record of what was acquired. Do not fabricate a partition to carry the county. Relaxing `partitions` is a widening and breaks nothing. Adding `jurisdiction` is **not**: make it required on both `ReleaseManifest` and `ReleaseManifest.from_acquisition`, and update the four construction sites, all in `libs/property-tax-adapters/tests/objectstore/test_s3_bronze.py`. Do not infer it from a non-empty partition tuple — that gives one fact two sources of truth and quietly reintroduces the derivation this lifecycle exists to remove.

Then carry the change through to what is actually written. `serialize_manifest` in the S3 adapter enumerates fields by hand, so a new dataclass field is not serialized, and the only county in the JSON today is `jurisdiction_code` inside each partition — which a zero-partition acquisition has none of. Emit the jurisdiction at the top level, and raise `BRONZE_MANIFEST_VERSION` to `2`, because the pinned version exists so a consumer can identify the manifest shape rather than infer it from which fields are present, and two shapes both calling themselves version 1 would defeat exactly that. Record what the versions mean: **v1** has a non-empty partition tuple and a county recoverable only from those partitions; **v2** carries an explicit jurisdiction and may carry no partition. Stored v1 objects are immutable and stay as they are — nothing in the repository deserializes a manifest today, so no stored object is re-read or rewritten, and none is migrated. Update the test asserting a serialized `manifest_version` of `1`.

Then fix the grain the manifest is stored at, which the explicit jurisdiction exposes. Two docstrings contradict each other today: `manifest_key` says "The manifest describes an artifact, so it is keyed like one" and writes `bronze/artifacts/<sha>.manifest.json`, while `ReleaseManifest` says it is "The immutable record of one acquisition". `record()` then treats an already-present manifest as success because "it describes the same artifact by construction" — sound while a manifest was artifact-grain, wrong once it carries a jurisdiction, a source URL, and an acquisition instant. The accepted artifact contract makes the collision reachable rather than theoretical: identity is the digest alone, so the same bytes acquired for `tx-dallas` and for `tx-collin` are one artifact and two acquisitions, and one key keeps only the first. That key also lets a stored v1 manifest block a v2 acquisition of those bytes forever, because the conditional put finds the old object and reports success.

Define the equivalence first, in `bronze.py`, because "idempotent per acquisition" means nothing until something decides when two recordings are one acquisition. Two are the same acquisition exactly when their retained acquisition evidence is equal: jurisdiction, artifact **content identity** (`StoredArtifact.sha256`), `acquired_at`, `source_url`, response metadata, redirects, `manifest_version`, and `tool_versions`, with `partitions` **excluded**, since partitions attach after recording and including them would make an acquisition look new for having gained one. Compare the artifact by digest alone. `StoredArtifact.locator`, `byte_count`, and `media_type` are **not** acquisition-defining, and the database is why: `bronze.artifact` is keyed by `sha256` and carries those three once per artifact, while `bronze.release_manifest` references it only by `artifact_sha256` and persists none of them — so a rule separating two same-digest acquisitions by locator or media type could not be honoured by `ManifestIndex` without a migration this change excludes, or without hidden cross-adapter state. Say what they are instead: the locator is artifact-grain storage evidence, the byte count artifact-grain integrity evidence, the media type artifact-grain metadata, and inconsistent artifact evidence for a digest already known is an artifact-consistency concern rather than a second acquisition identity. Every component that *is* acquisition-defining has an acquisition-grain home already — `jurisdiction_code`, `artifact_sha256`, `acquired_at`, `source_url`, `response_status`/`response_headers`, `bronze.release_redirect`, `manifest_version`, `tool_versions` — so the rule is one the index can actually honour. Expose that comparison on the value, so it is decidable from the immutable manifest alone with no locator, key, lock, digest choice, or query involved, and introduce no acquisition identifier separate from the manifest: a second identifier vocabulary is what D2a and D2c already refused. State the limit rather than over-promising: recordings whose retained evidence differs are different acquisitions even when the bytes are identical — the case artifact identity, being the digest alone, cannot distinguish and must not be asked to — but two physical fetches whose retained evidence is identical in every compared component are observationally equivalent and may coalesce, because the model carries no physical-attempt identifier. Do not add one, nor a column, nor a migration, to force them apart.

Then give acquisition manifests an acquisition-grain locator, leaving artifact bytes content-addressed. Require these properties and let the adapter choose the mechanism — do not fix a keying scheme in the port contract: the same acquisition recorded twice resolves to one manifest and writes no duplicate; a different acquisition of the same artifact resolves to a different manifest and neither displaces the other; an already-recorded manifest is never overwritten; and a stored earlier-shape manifest stays immutable without blocking a current-shape acquisition of the same bytes. Add hostile tests for each in `libs/property-tax-adapters/tests/objectstore/test_s3_bronze.py`, where the concrete storage assertions belong: the serialized v2 manifest shape including a jurisdiction on a zero-partition acquisition; two acquisitions of one digest for two jurisdictions both persisting with neither displaced; a v2 acquisition of an artifact whose stored manifest is v1 recorded without altering the v1 object; and — proving the mechanics are invariant to later partition knowledge — record an acquisition with zero partitions, attach a release partition separately, then re-register a `ReleaseManifest` carrying the same acquisition evidence *and* that partition, asserting the same acquisition-manifest locator is used and no second manifest object is created. That last one is what fails if an implementation digests the whole serialized manifest instead of a preimage excluding partitions. Keep these out of the application suite — task 7.2 proves contract properties over in-memory fakes and must not assert object keys or serialized JSON.

Do not change the `BronzeStore` Protocol. `reference_partition` already attaches a later-discovered partition and must still leave the recorded manifest untouched; note that it takes an artifact checksum, so in the object store a partition is associated with the **artifact**, while `ManifestIndex` associates it with the **acquisition** — deliberately different grains, and the docstrings should say so rather than implying one association.

## 3. Canonical persistence

<!-- countyforge-task: 3.1 paths=libs/property-tax-application/src/property_tax_application/canonical.py checks=repo.check risk=higher_risk prerequisites=D2,D5,D6,1.1 -->
- [ ] 3.1 Add the batch, its correlation, and the completion — Add `canonical.py` carrying `CorrelationHandle`, a frozen value over a positive integer unique within one `ReleaseLoadSession`, whose docstring states that it is neither domain identity nor persistence identity: it exists only to let a record name a parent, it never appears in a stored row, and it stops being resolvable once its account is complete. Session-wide uniqueness rather than per-account removes the ambiguity of one value meaning different things in different accounts. Make it enforceable: because the session releases a completed account's mapping, checking only what is currently live would let a later account mint a value an earlier one used, silently retargeting a late record at the wrong parent. Require handles to increase strictly over the session and have the session retain the highest yet introduced — a single integer, so the bound is untouched — refusing any handle that does not exceed it unless it is currently live. Retention still governs memory, and `still_needed` is how it is expressed: an implementation may release every mapping a batch does not declare. The canonical records hold their parents directly and **do not** gain a correlation field — they are domain types this change does not modify — so correlation rides on the batch instead: add `CorrelatedRecord`, a frozen pairing of one canonical record with `handle`, the value it may later be named by where it can be a parent, and `parent`, the value naming its own parent, both optional. Add `CanonicalRecordBatch`, a bounded tuple of `CorrelatedRecord` plus `continuing: CorrelationHandle | None` naming the one account, if any, left open at the end of the batch, and `still_needed: tuple[CorrelationHandle, ...]` naming the handles that must stay resolvable after it. `still_needed` is what actually bounds correlation, and without it the bound fails *inside* one account: an account with an unbounded number of owner associations whose allocations arrive later would keep every association mapping live until completion, so one-continuing-account bounds nothing by itself. With it, live mappings are bounded by the most recent declaration, which is bounded because the batch is — and a parent needed several batches later must be re-declared in each, which makes the cost visible rather than hidden. A parent is named the same way whether it sits in this batch or an earlier one, so there is one linkage mechanism and not two. Split validation by what each party can know. `CanonicalRecordBatch` is a frozen value that sees only itself, so validate there exactly the intrinsic shape: well-formed entries, no handle introduced twice within the batch, a `parent` naming a handle inside the batch resolving inside it, and at most one account named as continuing. Resolving is **not** enough: where the parent is in the batch, check that the handle denotes the very record the canonical value already holds — `OwnerValueAllocation.association` names one `OwnerAssociation`, and pairing it with a live handle for a different association would persist the allocation under a parent its own domain value does not name, which no database constraint can catch because both parents are legitimate. Compare by object identity, never by value, for the reason this task already gives. Do **not** ask the batch to judge handles opened by earlier batches or accounts already completed — it cannot know them, and a rule it cannot enforce is worse than none. The caller mints handles, strictly increasing over the session. Do **not** require a batch to carry an account's complete descent: the canonical model places no maximum on how many owners, allocations, values, exemptions, land records, improvements, or geometries an account may carry, so a whole-account batch would be bounded only by the largest account in the release, and inventing a maximum child count no accepted contract establishes would be worse. Do not assume every relation hangs off the snapshot — `canonical.owner_value_allocation` deliberately carries no `snapshot_key` and reaches its snapshot through its association, so an allocation's parent chain is two links deep. Use no generic mapping, JSON payload, free-form metadata attribute, or database-shaped row type, and define no key over observed values. Add `ReleaseLoadCompletion`, carrying the `ProcessingRunRef` and `already_complete: bool`. Add `UnknownAccountSnapshot`, the error raised when a parent offered for adoption has not been persisted.
