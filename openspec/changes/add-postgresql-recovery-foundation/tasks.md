## 4b. Review Corrections

Correct the configuration, the OpenSpec wording, the design diagram, and the tests together.
- [x] 4b.2 Add a built-image configuration parse gate — Execute the pinned pgBackRest binary from the built image against the committed configuration in a mode that parses configuration without reaching PostgreSQL or S3, and fail the gate on any `invalid option` or `invalid value` warning and on a missing resolved `--repo1-s3-process-cmd`. Assert on the warning text and the resolved option set rather than on exit status, which is zero either way. Prove by mutation that the previously undetected misspelling now fails.
- [x] 4b.3 Establish a readable, least-privilege certificate contract — A read-only mount proves immutability, not readability: the container's postgres user is uid 999 and the host key is owned by the operator, so `archive_command` would fail at runtime. Own the certificate directory and key by a dedicated GID, keep the key `0640` and never world-readable, never `0644`, never unrestricted, and never copied into an image, and join the PostgreSQL service to that GID as a supplementary group. Prove from the built container that postgres can read the key, that a container without the group cannot, and that the mount is still not writable. Add deterministic tests for the UID/GID/mode/mount contract.
- [x] 4b.4 Add a restore wrapper on the approved secret boundary — Resolve the cipher passphrase from Bitwarden inside the wrapper and pass it to Docker by reference as `-e NAME`, never as `-e NAME=value`, so it never reaches argv, shell history, or a process listing. Keep the Bitwarden access token host-only and out of Compose and containers. Give the recovered cluster the same pinned image, an isolated temporary volume, the read-only certificate mount and group, the backup ARNs, and a loopback-only non-production port, because reaching the target runs `archive-get` during startup and needs working credentials. Refuse the production volume by name and any Compose-managed volume by label.
- [x] 4b.5 Make the systemd units portable — Replace hard-coded operator account and home path with templates plus a deterministic install script that resolves the service user, repository path, and Docker group at install time, creates the certificate group at the configured GID, refuses to continue on an unsubstituted placeholder, and checks rather than grants Docker access. - [x] 4b.6 Correct the runtime-secret count accounting — Derive every reported count from the arrays that produce the secrets rather than restating a literal, so adding the next secret cannot reintroduce the drift, and test the reported count against the file actually written without exposing a value.
- [x] 4b.7 Repair the AWS runbook to match the procedure that worked — Use `aws --profile boss` for every administrator command and keep workload verification on `trupryce-data-vps` and `trupryce-backup`. Record the failures actually encountered: `us-east-1` must omit `--create-bucket-configuration`; the backup role ARN must be retrieved and validated rather than read from a stale shell variable; the Roles Anywhere profile must be created with `--enabled` and its ARN retrieved and validated afterwards. - [x] 4b.8 Add an actionable certificate expiry check — Report the not-after date and days remaining and exit non-zero inside the warning window, without claiming that renewal automation or alerting exists.

## 4d. Third-Round Review Corrections

- [x] 4d.1 Break the coupling between archive failure and database availability — Documenting the PID-1 orphan-reparenting mechanism does not remove it: any credential, network, or S3 failure leaving a daemonized pgBackRest worker exiting nonzero would restart the cluster again. Set `init: true` on the PostgreSQL service and `--init` on both isolated recovery containers so an init process reaps orphans instead of the postmaster. Prove the **behaviour**, not the YAML: reproduce the original credential failure, force WAL, and show archiving fails while the database stays up with zero restarts; then restore credentials and show the pending segment drains to S3.
- [x] 4d.2 Fail closed on a foreign certificate GID — Both installers accepted any existing group at the configured GID, so on a host where 2000 already belongs to, say, `developers`, the private key would be chgrp'd to that group at 0640 and every member could assume the platform's AWS identity. Add one shared helper used by both installers: accept only when the name and the number agree, refuse when the GID belongs to another group, refuse when the name exists at a different GID, and create it otherwise.
- [x] 4d.3 Make the clean-host runbook executable top to bottom — Move host prerequisites ahead of the step that enables archiving, because `identity.env` is a prerequisite of the async archive worker and was documented five sections after the restart that needs it. Add `infra/scripts/install-signing-helper.sh` for the pinned, checksum-verified host binary that `~/.aws/config` invokes, which no step previously installed. Make `bootstrap-env.sh` report the template values a new host must set, since it copies a blank profile ARN and Akamai-specific certificate paths verbatim. Replace the Hostinger prose with an explicit ordered sequence from host dependencies through timer installation and Akamai revocation.
- [x] 4d.4 Stop using `Conflicts=` as a mutex — `Conflicts=` is a negative dependency: starting the differential *stops* a running full backup rather than waiting for it. A Sunday full running past 03:30 would be terminated mid-backup, destroying the base every restore in the retention window depends on, and the longer it ran the likelier that became. Remove it, move the differential to Monday–Saturday so the two never contend on schedule, and keep `After=` for the `Persistent=true` catch-up case plus pgBackRest's own repository lock as defence in depth.
- [x] 4d.5 Correct the identity-file rationale — The file was introduced on the theory that the async worker runs with a cleaned environment. Instrumentation during the failure disproved that: five `TRUPRYCE_AWS_*` variables were present and the supplementary group was missing. Keep the file for reproducibility and to remove an assumption about what a daemonized worker inherits, and correct every place that asserted the disproved mechanism.

## 4f. Fifth-Round Review Corrections

- [x] 4f.1 Separate the drill contract from the promotion contract — `--promote` asserted on `public.recovery_marker`, a disposable testing artifact the runbook drops from production afterwards, so a real migration would restore successfully, fail assertions 5 and 6, and then destroy the restored volume. Keep the before/after markers mandatory for `--exercise`, which is the only assertion proving a chosen target was honoured, and give `--promote` a contract that a genuine cluster satisfies: databases, roles, recovery complete, a real write probe, and a migration-ledger check that tolerates a pre-migration cluster. Make `--target` optional for `--promote` so a migration restores to the end of the archive; a timestamp later than the last commit fails outright on an idle database.
- [x] 4f.2 Add a cutover write fence — A planned move restored, promoted, and started the new host before fencing the old one, so anything committed on the source after the restore target stayed on the old timeline and vanished silently. Airflow's scheduler alone writes continuously. Add `infra/scripts/cutover-fence.sh`: stop every Airflow writer, refuse to continue while any client backend remains connected, force the final WAL segment, wait for it to appear in S3, and report the recoverable boundary without cutting over. Put the fence before the restore in the procedure, and state that a disaster has nothing to fence.
- [x] 4f.3 Make promotion fail closed against process and host loss — The production-named volume was created before verification and cleaned up by an `EXIT` trap, which cannot run after `kill -9`, a reboot, or power loss. Label the volume at creation, which Docker writes atomically before any data exists, and write a verification sentinel only after every assertion and the write probe. Add a Compose preflight that refuses to start a promotion-labelled volume with no verified sentinel, leaving volumes without the label untouched.
- [x] 4f.4 Render the local AWS profiles from host configuration — The procedure told the operator to generate a new Hostinger certificate and then showed a profile block naming the Akamai certificate filenames. Add `infra/scripts/install-aws-profiles.sh`, deriving both profiles from `infra/.env`, writing mode 0600, storing no credential, and printing the certificate subject it wired up. Add the data-identity ARNs to the configuration so both halves come from one place, and replace the runbook's hand-authored block with placeholders and the renderer.
- [x] 4f.5 Harden the signing-helper fast path — A correct digest on a user-writable binary says nothing about what runs next. Require `root:root` ownership and a non-writable file and directory before accepting an existing binary, and reinstall otherwise.

## 4g. Sixth-Round Review Corrections

- [x] 4g.1 Move the promotion proof out of PGDATA — The verification sentinel was written into the restored data directory, which the next backup captures: measured as `pg_data/.trupryce-promotion-probe.zst` in a diff manifest, and observed coming back on a later restore. ## 4i. Eighth-Round Review Corrections

- [x] 4i.1 Freeze the source, not merely fence it — The fence left PostgreSQL running, so checkpoints, autovacuum, and administrative sessions kept generating and archiving WAL past the boundary it had just reported, and once the backup timers exist a scheduled backup of the old primary can land in the stanza after the new host has branched onto its own timeline, becoming the newest backup in the repository. Refuse to fence while any `pgbackrest-*` timer or service is active, naming the command that stops them rather than stopping an operator's schedule unasked, and stop the source cluster as the final step. Document rollback as the freeze in reverse.
- [x] 4i.2 Prove the stored credentials, not just LOGIN authority — Activation authenticated over the Unix socket, which `pg_hba.conf` maps to `trust`, so it proved only that `NOLOGIN` was lifted. It could not detect a recovery point predating a password rotation, where the role can log in and every runtime service still fails because Bitwarden holds a newer secret. Connect to the container's non-loopback address so `scram-sha-256` applies, once per role to the database it actually uses, with the password resolved through the existing Bitwarden boundary and passed by reference so it never enters argv. Report `LOGIN` authority and credential validity as separate claims.
