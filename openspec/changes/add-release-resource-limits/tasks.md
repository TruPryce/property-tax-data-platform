## 1. Peak-RSS Probe and Guard

Every task here depends on the `bounded-release-processing` capability being **implemented**, which it now is: the guard implements the `ResourceGuard` protocol that capability declares, and the tests drive the `process_release` it specifies, both present on `main`. No module or test belonging to that capability is modified here.

- [ ] 1.1 Add the peak-RSS probe and the guard that enforces a limit — Add `property_tax_adapters/resources/peak_rss.py` — a package **beside** `release`, not inside it, because the accepted boundary asserts per module that `property_tax_adapters.release` imports only `__future__`, `re`, `collections`, `contextlib`, `dataclasses`, `enum`, `types`, and `typing`, and a probe needs `resource` and a filesystem read. That is the correct architecture rather than a workaround: the boundary owns when it asks and deliberately owns no measurement. Provide a `PeakRssSource` `StrEnum` of exactly `cgroup_v2` and `rusage`; a frozen `PeakRssSample` carrying exactly a non-negative `peak_bytes: int` and a `source: PeakRssSource`; and `read_peak_rss() -> PeakRssSample` reading the cgroup v2 `memory.peak` resolved from the relative path in `/proc/self/cgroup` rather than assumed at the mount root, since a nested cgroup — every process under systemd, and every container under a delegated slice — has no such file at the root, and a measured host had none there while the file existed beneath its reported path, when readable and otherwise `max(getrusage(RUSAGE_SELF).ru_maxrss, getrusage(RUSAGE_CHILDREN).ru_maxrss) * 1024`, because `ru_maxrss` is KiB on Linux. Never use `tracemalloc`: one measured run reported 663 MiB traced against 2,079 MiB resident, and the OOM killer reads resident set size. Return the sample rather than a bare integer, so a figure always names the source that produced it and two measurements can be compared. Add `PeakRssGuard` taking a limit in bytes and implementing the accepted `ResourceGuard` protocol's `check(physical_rows_processed: int, staged_record_count: int) -> None`, sampling and raising when the peak is at or above the limit, so that a peak of exactly 900 MiB is refused by the guard and by the acceptance target alike rather than passing one and failing the other; it warns nothing, because the alternative to rejecting is being killed by the OOM killer, which produces no outcome, diagnostic, or progress event. Add no checkpoint, no boundary-visible state, and no field on any boundary type. Modify no module under `property_tax_adapters.release`. Import only the standard library and the accepted release protocols, and assert that `release` imports nothing from `resources`.

## 3. The Acceptance Benchmark

<!-- countyforge-task: 3.1 paths=benchmarks/release_peak_rss.py,Makefile checks=repo.check risk=higher_risk prerequisites=D31,D32,D36,D37,1.1,2.1 -->
- [ ] 3.1 Add the reproducible acceptance benchmark and its target — Add `benchmarks/release_peak_rss.py` taking **three** measurements, each in its own subprocess: a baseline `B` at 0 rows, `P1` at 250,000, and `P2` at 1,000,000, reading each peak through `read_peak_rss()`. Take every measurement from the `rusage` source in a separate subprocess, and fail closed if the three samples do not all name the same source. A separate process is necessary but not sufficient: siblings share a cgroup, and `memory.peak` is sticky and per-cgroup, measured at 4.88 GB on one host and unmoved by a child allocating 300 MiB, so three subprocesses reading it report one identical number and the ratio is 1.0 for a linear implementation as readily as a bounded one. `ru_maxrss` under `RUSAGE_SELF` is per-process — 314.6 MiB against a sibling's 17.0 MiB on the same host — and is the only source these three may use. The guard keeps preferring the cgroup, because there the cgroup is the container and its number is what the OOM killer acts on; the benchmark needs comparability between processes and the guard needs the authority the limit is enforced against. Compute `W1 = max(P1 - B, 0)`, `W2 = max(P2 - B, 0)`, and `scaling_ratio = (W2 + F) / (W1 + F)` with `F` a fixed 8 MiB noise floor, which is what keeps the quotient stable when both working sets are small rather than letting a few kilobytes of variance produce an arbitrary ratio. Apply two checks and fail if either fails: `P2` under 900 MiB, which supersedes the issue body's 1 GiB because the scheduler's measured 400 MiB peak shares the same 4 GiB container at a parallelism of four; and `scaling_ratio` at most **1.5**. The threshold follows from the shapes: rows increase fourfold, so a boundary retaining every row approaches 4.0 and one retaining nothing approaches 1.0, and 1.5 permits half the working set to grow while the row count triples — at most one sixth of proportional growth. Report the row count, the column count, `B`, `P1`, `P2`, `W1`, `W2`, the computed `scaling_ratio`, the source of each measurement and whether the three agreed, and the verdict of each of the two checks separately, so a reader can tell what was run rather than trusting that something was. Require no network. Add a `make` target invoking it, kept out of `make check` and out of the ordinary suite, because issue #43 D5 separates deterministic bounded CI tests from the acceptance command and a multi-minute allocation-heavy run would otherwise be paid on every commit.
