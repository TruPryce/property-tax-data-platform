## 1. Peak-RSS Probe and Guard

Every task here depends on the `bounded-release-processing` capability being **implemented**, which it now is: the guard implements the `ResourceGuard` protocol that capability declares, and the tests drive the `process_release` it specifies, both present on `main`. No module or test belonging to that capability is modified here.

- [ ] 1.1 Add the peak-RSS probe and the guard that enforces a limit — Add `property_tax_adapters/resources/peak_rss.py` — a package **beside** `release`, not inside it, because the accepted boundary asserts per module that `property_tax_adapters.release` imports only `__future__`, `re`, `collections`, `contextlib`, `dataclasses`, `enum`, `types`, and `typing`, and a probe needs `resource` and a filesystem read. That is the correct architecture rather than a workaround: the boundary owns when it asks and deliberately owns no measurement. Provide a `PeakRssSource` `StrEnum` of exactly `cgroup_v2` and `rusage`; a `PeakRssSourceUnavailable` exception carrying the requested source; a frozen `PeakRssSample` carrying exactly a non-negative `peak_bytes: int` and a `source: PeakRssSource`; and `read_peak_rss(source: PeakRssSource | None = None) -> PeakRssSample`, returning a sample from the named source when one is given — and raising a typed `PeakRssSourceUnavailable` carrying the requested `PeakRssSource` and no host path, rather than falling back — typed because the benchmark must catch exactly this to report the absolute indeterminate instead of crashing, and matching on message text is both forbidden and unstable — since substituting a source the caller did not ask for reproduces the vacuous ratio the naming exists to prevent — and otherwise reading the cgroup v2 `memory.peak` at the path resolved by joining the cgroup mount with what `/proc/self/cgroup` reports, never at an assumed root — a nested cgroup, meaning every process under systemd and every container under a delegated slice, has no such file at the root, and a measured host had none there while the file existed beneath its reported path, while a process in a cgroup namespace legitimately reports `/` and resolves to the root itself, which is correct rather than invalid — when that resolved path is readable and otherwise `max(getrusage(RUSAGE_SELF).ru_maxrss, getrusage(RUSAGE_CHILDREN).ru_maxrss) * 1024`, because `ru_maxrss` is KiB on Linux. Never use `tracemalloc`: one measured run reported 663 MiB traced against 2,079 MiB resident, and the OOM killer reads resident set size. Return the sample rather than a bare integer, so a figure always names the source that produced it and two measurements can be compared. Add `PeakRssGuard` taking a limit in bytes and implementing the accepted `ResourceGuard` protocol's `check(physical_rows_processed: int, staged_record_count: int) -> None`, sampling from the per-process `rusage` source and offering **no** cgroup mode — because the 900 MiB budget is per task while a shared container's cgroup measures the container, and a cgroup-reading guard would reject a compliant task, measured on one host as a 28.0 MiB process inside a cgroup peaking at 1,072.3 MiB; a cgroup mode would additionally need its subtree precondition re-verified at every checkpoint, since a process can join afterwards. Do not describe the guard as covering children: `RUSAGE_CHILDREN` counts only terminated, waited-for children and reports the largest rather than a sum — 0 MiB while two 300 MiB children were alive, 308 MiB after both were reaped — so it covers the current process plus a partial reaped-child signal and nothing more. Claim no single-process boundary: `PreparedReader` and `ReleaseStage` are caller-supplied protocols and nothing forbids a conforming one from spawning a subprocess, whose memory the guard cannot see. The isolated-cgroup benchmark stays authoritative, since a cgroup charges the whole subtree — exposing the most recent sample as `last_sample: PeakRssSample | None` with no history, `None` before the first check and set to the triggering sample **before** an over-limit check raises, so a rejection never exposes the previous checkpoint's figure, which is the only carrier available given that `check` returns `None`, a diagnostic has no source field, and D33 forbids boundary-visible state, and raising when the peak is at or above the limit, so that a peak of exactly 900 MiB is refused by the guard and by the acceptance target alike rather than passing one and failing the other; it warns nothing, because the alternative to rejecting is being killed by the OOM killer, which produces no outcome, diagnostic, or progress event. Add no checkpoint, no boundary-visible state, and no field on any boundary type. Modify no module under `property_tax_adapters.release`. Import only the standard library and the accepted release protocols, and assert that `release` imports nothing from `resources`.

- [ ] 3.1 Add the reproducible acceptance benchmark and its target — Add `benchmarks/release_peak_rss.py` taking **four** measurements — three for the scaling check and one for the absolute, which are not interchangeable. The three comparative ones run each in its own subprocess: a baseline `B` at 0 rows, `P1` at 250,000, and `P2` at 1,000,000, reading each peak through the probe. Take these three comparative measurements from the `rusage` source explicitly — `read_peak_rss(PeakRssSource.RUSAGE)`, since an unconditional cgroup preference would make this unimplementable on exactly the production-style host the benchmark models — each in a separate subprocess, and fail closed if the three samples do not all name the same source. Take the 900 MiB absolute from the **cgroup** instead, in a cgroup containing only that run, because issue #43 D5 makes the cgroup the authority the limit is enforced against and reporting a `rusage` figure against a cgroup-derived budget would be the very comparison this change calls invalid. Require caller-provided isolation and never create a cgroup or acquire privileges to measure itself; document the reproducible invocation `systemd-run --user --scope -p MemoryAccounting=yes make benchmark-release-peak-rss`, which on one measured host gave a fresh scope of three processes and a 2.2 MB peak where the ambient cgroup held six processes and 964 MB inherited from unrelated work, and note that a **purpose-built** container holding only this run may satisfy the requirement in place of the wrapper, subject to the same `cgroup.procs` verification — but that the Airflow container specifically does not, since the 900 MiB figure is derived from that container holding a scheduler and four concurrent tasks, so its cgroup contains siblings by construction and a peak read there is the container's rather than this run's. Verify the isolation rather than assume it, over the whole subtree: `memory.peak` charges a cgroup **and all of its descendants** while `cgroup.procs` lists only direct members, so a foreign process in a child cgroup raises the peak while appearing nowhere in that file. Require both that `cgroup.procs` for the cgroup named by `/proc/self/cgroup` list only this run's own process tree and that `cgroup.stat` report `nr_descendants 0` and `nr_dying_descendants 0` — dying included, since a cgroup being torn down can still hold charges. A fresh `systemd-run --user --scope` reported exactly that on one measured host, so the rule is satisfiable by the invocation recommended here. Where `cgroup.stat` is unavailable the subtree cannot be shown empty, so the absolute is indeterminate and the weaker `cgroup.procs`-only check is not substituted. Where no such cgroup can be established or verified, report the absolute as indeterminate, name why, do not substitute another source, do not report it as a pass, and exit non-zero — a run that could not measure the thing it exists to measure has not demonstrated the target, and an exit status read as success is how an unproven claim becomes a settled one. A separate process is necessary but not sufficient: siblings share a cgroup, and `memory.peak` is sticky and per-cgroup, measured at 4.88 GB on one host and unmoved by a child allocating 300 MiB, so three subprocesses reading it report figures describing the subtree rather than the reader — measured as 306.0, 449.5, and 454.2 MiB for siblings allocating 100, 200, and 400 MiB — none of which describes the process that read it, and whose spread is a function of when each read happened; compute no ratio from them, since they are not `B`, `P1` and `P2`, and the nondeterminism alone disqualifies the source. `ru_maxrss` under `RUSAGE_SELF` is per-process — 314.6 MiB against a sibling's 17.0 MiB on the same host — and is the only source these three may use. The guard reads `rusage` by default, because its 900 MiB budget is per task while a shared container's cgroup measures the container: measured on one host, a task whose own peak was 28.0 MiB sat in a cgroup peaking at 1,072.3 MiB, and a cgroup-reading guard would have rejected it. The benchmark's absolute may read the cgroup because it verifies isolation first, which makes that figure a per-task one. Apply two checks and fail if either fails: the **cgroup** peak at 1,000,000 rows under 900 MiB — not `P2`, which is a `rusage` figure and belongs only to the ratio — which supersedes the issue body's 1 GiB because the scheduler 419 MiB container peak with no task running shares the same 4 GiB container at a parallelism of four; and `scaling_ratio` at most **1.5**. The threshold follows from the shapes: rows increase fourfold, so a boundary retaining every row approaches 4.0 and one retaining nothing approaches 1.0, and 1.5 permits half the working set to grow while the row count triples — at most one sixth of proportional growth. Report the row count, the column count, `B`, `P1`, `P2`, `W1`, `W2`, the computed `scaling_ratio`, the separate cgroup figure the absolute check used, the source of each measurement, whether the three comparative ones agreed, whether the cgroup was verified isolated, and the verdict of each of the two checks separately including `indeterminate` where that is the answer, so a reader can tell what was run rather than trusting that something was.
