## 1. Peak-RSS Probe and Guard

Every task here depends on `add-bounded-release-processing` being **implemented**, not merely accepted: the guard implements a protocol that change's task 1.3 creates, and the tests drive a `process_release` its task 2.1 creates.

<!-- countyforge-task: 1.1 paths=libs/property-tax-adapters/src/property_tax_adapters/release/resources.py checks=repo.check risk=higher_risk prerequisites=D31,D32,D33,D34 -->
- [ ] 1.1 Add the peak-RSS probe and the guard that enforces a limit — Add `property_tax_adapters/release/resources.py` with a `PeakRssSource` `StrEnum` of exactly `cgroup_v2` and `rusage`; a frozen `PeakRssSample` carrying exactly a non-negative `peak_bytes: int` and a `source: PeakRssSource`; and `read_peak_rss() -> PeakRssSample` reading cgroup v2 `/sys/fs/cgroup/memory.peak` when readable and otherwise `max(getrusage(RUSAGE_SELF).ru_maxrss, getrusage(RUSAGE_CHILDREN).ru_maxrss) * 1024`, because `ru_maxrss` is KiB on Linux. Never use `tracemalloc`: one measured run reported 663 MiB traced against 2,079 MiB resident, and the OOM killer reads resident set size. Return the sample rather than a bare integer, so a figure always names the source that produced it and two measurements can be compared. Add `PeakRssGuard` taking a limit in bytes and implementing the accepted `ResourceGuard` protocol's `check(physical_rows_processed: int, staged_record_count: int) -> None`, sampling and raising when the peak exceeds the limit; it warns nothing, because the alternative to rejecting is being killed by the OOM killer, which produces no outcome, diagnostic, or progress event. Add no checkpoint, no boundary-visible state, and no field on any boundary type. Import only the standard library and the accepted release protocols.

- [ ] 1.2 Add deterministic bounded tests for the probe and guard — Cover the source precedence with the cgroup path readable and with it absent or unreadable, asserting the reported source in each case and that the `rusage` figure is the documented `max(SELF, CHILDREN) * 1024`. Assert `PeakRssSample` declares exactly its two fields, is frozen, and that no code path returns a bare integer instead. Assert `tracemalloc` appears nowhere in the module. Assert `PeakRssGuard` raises above its limit and not below, that a raising guard surfaces through the accepted boundary as `resource_limit_exceeded` and not as another code, and that the release is aborted with `committed_record_count` zero. Assert the guard is called at exactly the checkpoints the accepted boundary fixes on a 250,000-row release — after the stage is entered, at each 100,000 boundary, and once at end-of-input — and adds none. ## 2. Streaming Synthetic Release at Scale

<!-- countyforge-task: 2.1 paths=libs/property-tax-adapters/tests/release/scale.py checks=repo.check risk=higher_risk prerequisites=D35,1.1 -->
- [ ] 2.1 Add the streaming synthetic release generator — Add `scale.py` providing a reader satisfying the accepted `PreparedReader` protocol over generated data, producing at least 1,000,000 physical rows with at least 90 source columns for the acceptance run and any smaller size on request. Yield `SourceRowEnvelope` values directly from a counter: write nothing to disk, because a million rows at ninety columns is roughly a gigabyte of text, committing it is forbidden by the artifact policy, and staging it in a temporary file would measure the filesystem rather than the boundary. Retain no row already yielded and hold no state that grows with the row count, so the instrument does not itself hold the release it measures. Produce synthetic, identity-free, redistribution-safe values only, with no county bytes, owner values, addresses, or production rows.

## 3. The Acceptance Benchmark

<!-- countyforge-task: 3.1 paths=benchmarks/release_peak_rss.py,Makefile checks=repo.check risk=higher_risk prerequisites=D31,D32,D36,D37,1.1,2.1 -->
- [ ] 3.1 Add the reproducible acceptance benchmark and its target — Add `benchmarks/release_peak_rss.py` driving `process_release` over the synthetic reader at **two** sizes, 250,000 and 1,000,000 physical rows, reading the peak through `read_peak_rss()` after each. Require the 1,000,000-row peak to be under 900 MiB, which supersedes the issue body's 1 GiB because the scheduler's measured 400 MiB peak shares the same 4 GiB container at a parallelism of four. Require the peak not to scale with the row count: the fourfold row increase between the two sizes is what distinguishes a flat peak from a linear one, and a single absolute cannot, since an implementation retaining every row can pass one threshold on a large enough machine and fail at the next order of magnitude. Report the row count, the column count, the measured peak for each size, the source of each measurement, and whether the target was met, so a reader can tell what was run rather than trusting that something was. Require no network. Add a `make` target invoking it, kept out of `make check` and out of the ordinary suite, because issue #43 D5 separates deterministic bounded CI tests from the acceptance command and a multi-minute allocation-heavy run would otherwise be paid on every commit.
